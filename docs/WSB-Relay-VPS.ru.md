# Реле на VPS — режим без Cloudflare

Дата: 22.11.2026. Контекст: `*.workers.dev` недоступен из сети РФ (Safari на
iPhone не открывает воркер), поэтому pipe-режим через CF Worker отпадает.
Альтернатива уже встроена в приложение: в поле «CF Worker» можно указать
`host:port` — тогда трафик идёт **напрямую на ваш VPS**, без CF, без WS, без TLS.

Сервер: [`wsb-relay.py`](./wsb-relay.py) — один файл, чистый Python 3.8+,
без зависимостей. Протестирован локально: парсинг заголовка, обе трубы,
отклонение неверного секрета, dial-failure.

## Протокол (жёстко соответствует `WSClient.connectRelay`)

```
iPhone -> VPS:  "wsb1 <IPv4>\n"  затем сырой obfuscated2-поток MTProto
VPS -> Telegram: TCP <IPv4>:443, байты в обе стороны без изменений
```

Секрет фиксированный `wsb1` — клиент шлёт его сам ([WSClient.swift:89](../Tunnel/WSClient.swift)),
менять нельзя без правки приложения. Реле видит только зашифрованный
obfuscated2-поток; ключей и содержимого там нет.

## Установка на VPS (2–3 минуты)

```bash
# 1. положить файл
scp docs/wsb-relay.py user@vps:/opt/wsb-relay.py

# 2. systemd-юнит
sudo tee /etc/systemd/system/wsb-relay.service <<'EOF'
[Unit]
Description=WSBridge raw TCP relay
After=network-online.target
Wants=network-online.target

[Service]
ExecStart=/usr/bin/python3 /opt/wsb-relay.py --port 8443
Restart=always
RestartSec=3
DynamicUser=yes
NoNewPrivileges=yes
ProtectSystem=strict
ProtectHome=yes

[Install]
WantedBy=multi-user.target
EOF
sudo systemctl daemon-reload
sudo systemctl enable --now wsb-relay
sudo systemctl status wsb-relay --no-pager
```

Порт `8443` выбран неслучайно: он похож на HTTPS-ALT и не входит в топ
«подозрительных» портов. Открыть его в фаерволе:
`sudo ufw allow 8443/tcp` (или аналог вашего фаервола).

## Подключение в WSBridge

Меню → **CF Worker** → вписать `IP_вашего_VPS:8443` (туннель выключен) → включить.
Формат `host:port` распознаётся автоматически ([TunnelSession.swift:205](../Tunnel/TunnelSession.swift))
и включает relay-режим вместо pipe.

## Замаскировать под «рабочий» сервис

Вы правы, что голый непонятный порт может привлечь внимание хостера. Три
варианта по возрастанию сложности:

1. **Ничего не делать.** Один-два пользователя, десятки соединений в день,
   ~мегабайты трафика — это шум ниже порога любых автоправил. Самый честный
   совет: сначала так.
2. **Порт 443.** Если на VPS больше нет веб-сервера, повесьте реле прямо на
   `--port 443`. Внешне это «какой-то TCP на 443», DPI без глубокой инспекции
   не отличит его от HTTPS до первого пакета — а первый пакет это
   `wsb1 <ip>\n`, не HTTP, так что классификаторы HTTP его просто
   проигнорируют как «не-HTTP».
3. **TLS-обёртка** (нужна правка приложения): завернуть реле в TLS с
   настоящим сертификатом Let's Encrypt — тогда это неотличимо от обычного
   HTTPS-сайта. Но `connectRelay` сегодня шлёт сырой TCP, так что это уже
   этап с изменением кода; не предлагаю до подтверждения, что базовый
   relay-режим вообще работает у вас.

## Что смотреть в журнале

| Строка | Значит |
|---|---|
| `cfg:worker=<ip>:8443(x1)` | настройка доехала |
| `pipe:conn<N>:<IP>` | сессия в relay-режиме, `<IP>` — куда дозванивается реле |
| `relay_up` | TCP до VPS открыт, заголовок отправлен |
| `ws_up` | **пришли первые байты от Telegram через VPS** — успех |
| `relay_slow` | VPS не ответил за 5 с — порт закрыт/фаервол |
| `relay_closed:...` | соединение закрыто; см. лог реле на VPS |

На самом VPS: `journalctl -u wsb-relay -f` — там видно каждый коннект,
`up=/down=` байты и `reply=True/False` (ответил ли DC).

## Ограничения

- Реле в РФ: если хостер получит жалобу — риск блокировки VPS. Вы это сами
  отметили; вариант «сначала ничего не маскировать» держит профиль низким.
- Один процесс, один порт; для 1–2 пользователей этого достаточно.
- `IDLE_TIMEOUT=300` сек: соединение без трафика 5 минут закрывается реле.
  Telegram сам держит свои соединения активными, так что на практике
  обрывов быть не должно.
