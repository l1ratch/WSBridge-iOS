# WSBridge · Роутинг по доменам через собственный DoH (концепция D)

> Статус: **утверждается**, код не менялся, коммита/пуша нет.
> Последняя опубликованная сборка — `0.3.16`.
> Незапушенный эксперимент с 26 CIDR + IPv6 лежит в рабочем дереве и в эту
> концепцию **не входит** (откатывается на этапе 0).

---

## 0. Почему вообще меняем архитектуру

Три сборки попыток перехватить DNS внутри `NEPacketTunnelProvider` провалились
по одной причине, зафиксированной логами:

```
dnsprobe:... udp53=0 done=0 dst=[-]
```

Сырые UDP:53 **не приходят в `packetFlow`**. Системный DNS живёт в
`mDNSResponder` выше `utun`; с `matchDomains=[""]` iOS послушно считает
`198.18.0.3` резолвером, но ответа от него не получает → «все сайты мертвы».
Без `dnsSettings` сайты живут, но список доменов нечем применить.

**Вывод:** туннель не может быть DNS-сервером. DNS-решение выносится туда,
где iOS его реально видит — в `NEDNSOverHTTPSSettings` (системный DoH).
Туннель становится только «исполнителем метки».

Сравнение отклонённых вариантов:

| | Универсальность | Батарея | Второй таргет | Замена lwIP |
|---|---|---|---|---|
| Узкие CIDR (было) | ❌ только известные AS | ✅ | нет | нет |
| `0/0` + direct | ✅ | ❌ весь трафик userspace | нет | **да** |
| `NEDNSProxyProvider` | ✅ | ✅ | **да** | нет |
| **D: свой DoH + FakeIP-метка** | ✅ | ✅ | нет | нет |

## 1. Итоговая схема

```
Приложение (Main App)
  ├─ поля: «Адрес воркера» (голый host), HWID (read-only), выбранные списки
  ├─ САМО склеивает serverURL = https://<host>/dns-query/<HWID>
  │    (сегмент списков НЕ передаём — расширение, см. §1.2)
  ├─ САМО отдаёт системе dnsSettings = DoH на воркер
  │    с matchDomains = ТОЧНЫЕ домены из включённых списков (Вариант Б)
  │    → воркер видит ТОЛЬКО их; весь остальной DNS резолвится системой
  │      (выборщик DNS в приложении, по умолчанию «Системный»)
  ├─ резолвит <host> в IP заранее (getaddrinfo, ДО включения туннеля)
  └─ includedRoutes: Telegram DC + 198.18.1.0/24  (узко!)
     excludedRoutes: IP воркера + IP socks5-прокси

Воркер (отдельная ветка worker/, wrangler.toml, БЕЗ KV/панели/cron)
  ├─ ОСНОВНОЙ РЕЖИМ (по умолчанию): НЕ знает ни про какие списки.
  │    Любой валидный DNS-запрос → A = 198.18.1.1 (метка, ОДИН адрес на всё)
  ├─ защита: HWID ∉ TRUSTED_IDS → DNS-wire REFUSED (200)
  │    (параметр REQUIRE_ID = false в wrangler.toml её ОТКЛЮЧАЕТ)
  └─ /diagnose → структурированный JSON (для кнопки «Тест воркера»)

Туннель (PacketTunnelProvider)
  ├─ 198.18.1.1 → lwIP → TLSSNI(ClientHello) → ProxyClient CONNECT по ИМЕНИ → socks5/http
  ├─ Telegram DC → WSBridge (не трогаем)
  └─ реальные IP → мимо utun (батарея не тратится)
```

**Два упрощения, которые это даёт:**

1. FakeIP — **не мапа, а метка**. Домен достаётся из SNI, а не из IP.
   `domainByFakeIP`, LRU, `prefix(250)`, `MAX 254` не нужны вообще.
2. **Фильтрация по доменам живёт ровно в одном месте** — в `matchDomains`
   на iOS. Воркер не читает `.lst`, не тянет GitHub, не строит `Set`, не
   знает про `id` списков. Меньше кода, меньше кэша, меньше мест для
   рассинхрона «список в приложении ≠ список в воркере».

## 1.1. Вариант Б (основной) и Вариант А (резервный)

### Б — принят к реализации

`NEDNSOverHTTPSSettings.matchDomains` = **ТОЧНЫЕ домены из включённых
списков**, без какого-либо агрегирования/упрощения.

- iOS направляет на воркер **только** запросы по этим именам;
- всё остальное резолвится **системой** — тем самым DNS, что выбран в
  обычном выборщике приложения (по умолчанию «Системный», §6.4);
- воркер физически не видит чужой и произвольный трафик → защита от «злых
  целей» архитектурная, а не только allowlist HWID;
- **воркер НЕ проверяет QNAME по спискам**: раз iOS уже отфильтровала,
  любой дошедший запрос получает FakeIP. Проверка в одном месте, без
  дублирования;
- `UPSTREAM_DOH` в основном режиме **не нужен** (см. §1.2, где он
  понадобится);
- выборщик DNS сохраняет смысл при включённом режиме прокси-доменов.

**НИКАКОГО eTLD+1 / «google.com вместо gemini.google.com».** Запрещено
явно: агрегат `google.com` потянул бы на воркер (и потенциально в прокси)
весь Google — это и лишняя нагрузка на трафик, и риск незахвата
критичного домена из-за размытого правила. Список из `.lst` передаётся
**как есть, по одному имени на запись** в `matchDomains`.

`matchDomains=[""]` (все имена) **не используется ни в Б, ни в А** — именно
он в `0.3.14` убивал сайты.

### А — резервный, НЕ реализуется сейчас

Снять `matchDomains` entirely → весь DNS телефона идёт на воркер.
Тут **и понадобится** расширение из §1.2: приложение начинает передавать
активные списки в URL, воркер отвечает FakeIP только для них, а остальные
запросы форвардит на обязательный `UPSTREAM_DOH`. Выборщик DNS в
приложении перекрывается воркером.

**Держим как план отката**, если на этапе 2 или 5 выяснится, что iOS не
отдаёт на воркер часть доменов из списков (не применила `matchDomains`,
урезала path, резолвит мимо). Переключение — **одна строка** в
`startTunnel` (убрать `matchDomains`) + включить режим «списки в URL» из
§1.2. Воркер при этом **уже умеет** оба режима (§1.2), поэтому архитектура,
контракт URL, `/diagnose` и UI не переписываются.

Критерий отката: в логах воркера нет запросов по домену из включённого
списка, при этом `dnsSettings` применён и `/diagnose` зелёный.

## 1.2. Два режима воркера: простой (сейчас) и по спискам (расширение)

Воркер пишется сразу с двумя режимами, но **по умолчанию включён первый**.
Переключатель — `MODE` в `wrangler.toml`; приложение управляет им через
наличие/отсутствие сегмента списков в URL.

### Режим 1 `MODE = "simple"` — ОСНОВНОЙ, реализуется на этапе 1

```
URL:  https://<host>/dns-query/<HWID>
```

| Условие | Ответ |
|---|---|
| `REQUIRE_ID = true` и HWID ∉ `TRUSTED_IDS` | DNS REFUSED (HTTP 200) |
| **любой** валидный DNS-запрос (POST или GET) | A = `198.18.1.1`, TTL 60 |

Никаких `.lst`, `LISTS`, `caches.default`, `UPSTREAM_DOH`, `id` списков,
сегмента `<sets>` в URL. Воркер — ~80 строк. `wrangler.toml`:

```toml
[vars]
MODE = "simple"
REQUIRE_ID = "true"          # false = ОТКЛЮЧИТЬ защиту по ID (для отладки/доверенной сети)
TRUSTED_IDS = "9F3CA71-…,D4E5F6-…"
FAKE_IP = "198.18.1.1"
```

`REQUIRE_ID = false` — **явный параметр отключения защиты**, как ты и
просил. В `/diagnose` при этом пишется `errors: [{code:"ID_CHECK_DISABLED"}]`,
чтобы человек видел, что воркер открыт.

Безопасность простого режима держится на двух уровнях: `matchDomains` на
iOS (воркер не видит чужие домены) + `TRUSTED_IDS` (чужое устройство
получает REFUSED). Отключив `REQUIRE_ID`, пользователь осознанно оставляет
только первый уровень — это его выбор, зафиксированный в конфиге.

### Режим 2 `MODE = "lists"` — РАСШИРЕНИЕ, НЕ реализуется сейчас

```
URL:  https://<host>/dns-query/<HWID>/google-ai+youtube+discord
```

- приложение передаёт **активные списки** в path (формат из §2 с `+`);
- воркер тянет `.lst` по `LISTS` с кэшем `caches.default` (§5), строит `Set`
  точных доменов — **без агрегации**;
- QNAME точно в `Set` → FakeIP; иначе → `UPSTREAM_DOH` (обязательный);
- `UNKNOWN_LIST` → в `listsIgnored` в `/diagnose`, не роняет запрос;
- `DENY_SETS = ["telegram"]` (§4).

**Когда включаем:** (а) как дальнейшее развитие функционала, если
понадобится фильтровать уже на сервере; (б) автоматически при откате на
**Вариант А** — там без этого весь интернет получил бы FakeIP.

### Почему так удобно

Основной режим не зависит от GitHub, от синхронизации `id`, от размера
списков и от доступности апстрима. Ветка `worker/` на этапе 1 — один файл
+ `wrangler.toml` + README. Всё, что связано со списками на сервере,
отложено и изолировано в режиме 2, а не размазано по коду.

## 2. Контракт URL — всё в path, НОЛЬ query

### Обоснование (RFC 8484, проверено)

- **§3** «The DoH client is configured with a URI Template… Configuration…
  is done out of band» — `NEDNSOverHTTPSSettings.serverURL` и есть этот
  сконфигурированный URI. Приложение задаёт его целиком.
- **§3** «DoH servers MAY support more than one URI Template. This allows the
  different endpoints to have different properties, such as different
  authentication requirements» — ровно наш случай: свой path на
  устройство + набор списков.
- **§4.1** «The URI Template… is processed **without any variables when the
  HTTP method is POST**». Пример POST в §4.1.1: `:path = /dns-query` —
  статический path доходит гарантированно.
- **§4.1.1** `?dns=…` добавляется **только для GET**. Для POST клиент ничего
  в query не добавляет.
- **§4.1** «A DoH server MUST implement both POST and GET» — воркер обязан
  уметь оба.

**Следствие (сомнение пользователя подтвердилось):** произвольные `&param=…`
в query для POST стандартом не определены, и Apple-клиент вправе их
нормализовать/отбросить. Поэтому **query не используем вовсе**.

### Формат

**Основной режим (`MODE = "simple"`, этап 1):**

```
https://<голый host>/dns-query/<HWID>
```

**Расширение (`MODE = "lists"`, §1.2) — тот же URL плюс сегмент списков:**

```
https://<голый host>/dns-query/<HWID>/<list-id-1>+<list-id-2>+...
```

- разделитель списков `+` (валиден в path, не превращается в пробел — это
  свойство только query); `id` списков содержат дефис (`google-ai`), поэтому
  `-` как разделитель нельзя;
- HWID — UUID без дефисов или с ними, без `/`;
- **двойной `/` (несколько сегментов) работает**: path — просто строка,
  ограничений на число сегментов нет. `url.pathname.split('/')` даст два
  элемента в простом режиме и три в режиме списков. Важно только не
  допускать **пустого** сегмента (`//` подряд) и не кодировать `+`;
- примеры: `https://wsb-doh.example.workers.dev/dns-query/9F3C…A71` и
  `…/dns-query/9F3C…A71/google-ai+youtube+discord`;
- в **простом режиме** воркер читает только `parts[1]` (HWID) и вообще не
  смотрит на остальные сегменты. Поэтому приложение может хоть сейчас
  передавать списки — на поведение это не повлияет до включения `MODE="lists"`;
- в режиме списков неизвестный `id` → игнорируется, не роняет запрос.

### Разбор на воркере

```js
const parts = url.pathname.split('/').filter(Boolean);
// ["dns-query", "<HWID>"]                      — простой режим
// ["dns-query", "<HWID>", "google-ai+youtube"] — режим списков
const hwid = parts[1];
const requested = (parts[2] || '').split('+').filter(Boolean);  // только MODE="lists"
```

QNAME (домен, который спрашивает приложение, напр. `gemini.google.com`)
приходит **не в URL**, а в теле запроса: POST — бинарный DNS-wire
(`application/dns-message`, RFC 8484 §4.1.1: 33 байта, где внутри лежат
метки `03 77 77 77 07 65 78…`), GET — `?dns=<base64url>` (§6).
Ссылка несёт только адрес воркера + HWID (+ опционально id списков); сам
вопрос «какой IP у этого домена?» воркер вытаскивает из тела: 12-байтовый
DNS header + length-prefixed labels, ~25 строк JS без зависимостей. Поэтому
`/diagnose` показывает `parsed.qname`, но система не «передаёт домен в
ссылку». **В простом режиме QNAME нужен только для `/diagnose` и логов —
на ответ он не влияет** (FakeIP выдаётся любому валидному запросу).
Воркер поддерживает оба метода (§4.1 RFC: «A DoH server MUST implement
both the POST and GET methods»).

### Бутстрап (RFC 8484 §10)

«a DoH client cannot use its DoH server to initially resolve the server's
host name into an address… 1) making the initial resolution part of the
configuration». Поэтому:

- `NEDNSOverHTTPSSettings(servers: [IP])` — **числовой IP**, резолвится в
  Main App до включения туннеля;
- `serverURL` содержит hostname для TLS/SNI;
- IP воркера обязательно в `excludedRoutes`, иначе DoH-коннект уедет в `utun`
  и закольцуется. Сейчас исключается только IP socks5-прокси — добавить.

## 3. Контракт ответов воркера

### 3.1. Системный путь `/dns-query/...`

RFC 8484 §4.2.1: «A successful HTTP response with a **2xx** status code is
used for any valid DNS response, **regardless of the DNS response code**…
HTTP responses with non-successful HTTP status codes do not contain replies
to the original DNS question» (и провоцируют ретрай).

Значит **нельзя** отдавать JSON или HTTP 403 в ответ на системный DoH —
иначе повторится «все сайты умерли». Всегда `200` +
`Content-Type: application/dns-message` + валидный DNS-wire:

| Ситуация | DNS rcode | Тело |
|---|---|---|
| **Простой режим (`MODE="simple"`), HWID ок, любой валидный запрос** | NOERROR (0) | A `198.18.1.1`, TTL 60 |
| `REQUIRE_ID = true`, HWID ∉ `TRUSTED_IDS` | REFUSED (5) | пустой ответ |
| `REQUIRE_ID = false` (защита выключена) | NOERROR (0) | A `198.18.1.1` — отвечаем всем |
| Битый wire / не тот content-type | FORMERR (1) | пустой ответ |
| **Режим `MODE="lists"` (расширение, §1.2)**: QNAME точно в `.lst` | NOERROR (0) | A `198.18.1.1` |
| Там же: QNAME не в `.lst`, апстрим ок | как у апстрима | ответ апстрима |
| Там же: QNAME не в `.lst`, апстрим упал | SERVFAIL (2) | пустой ответ |

В простом режиме **`UPSTREAM_DOH` не вызывается вообще** — форвардинг
существует только в коде режима `lists`. Это и есть то упрощение, которое
убирает зависимость от доступности апстрима и GitHub.

Дополнительно (не обязательно, но удобно): продублировать диагностику в
заголовок `X-WSBridge-Debug: <base64(json)>` — клиенту не мешает, в логах
видно. `Cache-Control: max-age` ≤ минимальному TTL (§5.1), для FakeIP — 60.

### 3.2. Тестовый путь `/diagnose` — структурированный JSON

Отдельный endpoint, дёргается **кнопкой «Тест воркера»** через обычный
`URLSession` из приложения (не через системный DoH). Возвращает то, что
воркер распознал, и все ошибки списком:

```json
{
  "ok": false,
  "version": "1",
  "parsed": {
    "hwid": "9F3CA71-…",
    "hwidTrusted": false,
    "mode": "simple",
    "requireId": true,
    "listsRequested": [],
    "listsActive": [],
    "listsIgnored": [],
    "path": "/dns-query/9F3CA71-…",
    "method": "POST",
    "contentType": "application/dns-message",
    "qname": "gemini.google.com",
    "qtype": "A",
    "wouldAnswer": "198.18.1.1"
  },
  "config": {
    "mode": "simple",
    "requireId": true,
    "trustedIds": 2,
    "fakeIp": "198.18.1.1",
    "upstream": null,
    "listsConfigured": 0,
    "listsLoaded": 0,
    "cache": "n/a"
  },
  "errors": [
    { "code": "HWID_NOT_TRUSTED", "message": "Добавь этот HWID в TRUSTED_IDS" }
  ]
}
```

В режиме `MODE="lists"` тот же JSON дополнительно заполняет
`listsRequested/Active/Ignored`, `upstream`, `listsConfigured/Loaded`,
`cache` и может вернуть `UNKNOWN_LIST` / `UPSTREAM_UNAVAILABLE`.
При `REQUIRE_ID = false` добавляется
`{ "code": "ID_CHECK_DISABLED", "message": "Защита по ID отключена в wrangler.toml" }`,
чтобы человек видел, что воркер открыт.

`GET /diagnose` без тела → та же структура с `qname:null` (проверка
«воркер жив, HWID принят, режим тот, что ожидался»). Кнопка в приложении
показывает `ok`, режим, `wouldAnswer` и `errors` человеческим текстом.

**RFC-совместимость:** `/diagnose` — обычный JSON API на том же воркере, не
DoH-endpoint; системный резолвер его не дёргает, `application/dns-message`
там не ожидается. Конфликта нет.

## 4. Приоритет Telegram — ЖЁСТКОЕ ПРАВИЛО

**Система Telegram не трогается ни в коем случае.** Это суть приложения,
базовый функционал наравне с обычным выборщиком DNS. Все `CFDomains`,
`WSClient`, `InitParser`, `MsgSplitter`, `AESCTR`, `TelegramDCs.swift`,
`TunnelSession.startWS/startPipe`, `lwip_bridge.c` остаются как есть.

Конфликт, который надо закрыть явно: в 12 пресетах itdoginfo есть
`Services/telegram.lst` (домены `t.me`, `web.telegram.org`, …). Если
пользователь включит его — воркер выдаст FakeIP, и соединение уйдёт в
socks5 вместо WSBridge. Этого быть не должно.

**Правило приоритета (три уровня, все обязательны):**

1. **Маршрутизация ядром iOS — самый старший.** `TelegramDCs.includedRoutes`
   (`149.154.0.0/16`, `91.108.0.0/16`, `91.105.192.0/24`) всегда в
   `includedRoutes`. Telegram-клиент ходит по **зашитым IP датацентров**, а не
   по DNS, поэтому его TCP-пакеты физически приходят в туннель с `dcIP` из
   этих подсетей. `handleAccept` проверяет их **ПЕРВЫМ** условием и
   направляет в WSBridge-ветку (`startWS` / `startPipe`) независимо от того,
   что нарешал воркер. Никакой SNI-парсер, ни `198.18.1.x` их не перехватывают.
2. **Пресет `telegram` исключён из выбора списков прокси-доменов.** В
   `ProxyDomainsView` он не показывается (или показан серым с подписью
   «Telegram обрабатывается WSBridge, прокси не нужен»). При сборке
   `matchDomains` приложение в любом случае выкидывает `id == "telegram"`,
   даже если старое значение залежалось в `enabledProxyListIds`. **Это
   главный уровень защиты в простом режиме**: раз воркер отвечает FakeIP на
   любой дошедший запрос, телеграм-домены просто не должны попасть в
   `matchDomains`.
3. **Защитный deny-list в воркере — только для режима `MODE="lists"`**
   (§1.2). `DENY_SETS = ["telegram"]`, unknown/denied → в `listsIgnored` в
   `/diagnose`, FakeIP не выдаётся. В простом режиме воркер списков не знает,
   поэтому этот уровень не работает — но он и не нужен при исправном
   уровне 2.

**Следствие:** «прокси-домены» и «система Telegram» — непересекающиеся
множества по построению. Пользователь не может сломать ТГ, включив список.
В этапе 5 это проверяется отдельным тестом.

Также: пользовательские кастомные списки могут содержать телеграм-домены —
на уровне 2 их не отсечь. Поэтому уровень 1 (приоритет по IP) является
**главным и достаточным**: даже если `t.me` получит FakeIP и уйдёт в
`198.18.1.1`, это затронет только веб-ссылки/логин по домену, но **не**
MTProto-трафик датацентров. Уровень 3 всё же оставляем для чистоты логов.

## 4.1. HWID — что это на самом деле

Не «адрес устройства» в смысле MAC/UDID:

- **UDID** запрещён Apple с 2013, **MAC** недоступен с iOS 7,
  **IDFA** требует ATT-промпт;
- легальный вариант без разрешений — **`UIDevice.current.identifierForVendor`**
  (IDFV): UUID, уникальный для пары *(вендор, устройство)*;
- **меняется**, если удалить все приложения этого вендора / переустановить;
- не переживает удаление приложения → доступ автоматически отзывается
  (ровно поведение allowlist в AdGuardHome, которое и легло в идею).

Фиксация: называть в UI **«ID устройства»** (не «HWID/адрес»), хранить
нередактируемым, в инструкции явно написать «после переустановки ID
изменится — добавь новый в `TRUSTED_IDS`, старый можно удалить».
Никакого общего `SHARED_SECRET` не нужно: у каждого свой воркер и свой
allowlist, красть нечего.

## 5. Конфиг воркера (без панели / KV / cron)

`wrangler.toml` в ветке `worker/`, правится руками при деплое.
**По умолчанию — простой режим**; поля для списков закомментированы и на
этапе 1 не используются:

```toml
name = "wsbridge-doh"
main = "src/index.js"
compatibility_date = "2026-01-01"

[vars]
MODE = "simple"                              # "simple" | "lists" (§1.2)
REQUIRE_ID = "true"                          # false = ОТКЛЮЧИТЬ защиту по ID
TRUSTED_IDS = "9F3CA71-…,D4E5F6-…"           # allowlist, через запятую
FAKE_IP = "198.18.1.1"

# --- Ниже ТОЛЬКО для MODE = "lists" (расширение / Вариант А) ---
# UPSTREAM_DOH = "https://cloudflare-dns.com/dns-query"
# DEFAULT_SETS = "google-ai"
# DENY_SETS = "telegram"
# CACHE_TTL = "21600"
# LISTS = '''
# { "google-ai": "https://raw.githubusercontent.com/itdoginfo/allow-domains/main/Services/google_ai.lst", ... }
# '''
```

**Простой режим не зависит ни от чего внешнего:** нет GitHub, нет апстрима,
нет кэша. Если воркер жив — он отвечает. Поэтому в нём невозможно повторить
«все сайты умерли» из-за недоступности `1.1.1.1`.

**Для режима `MODE="lists"` (расширение, НЕ этап 1):** `UPSTREAM_DOH` —
DoH-URL, не голый IP (CF Worker не умеет UDP:53); воркер форвардит тот же
DNS-wire POST-ом. Списки тянутся с `caches.default` — `cache.match(listURL)`
→ при miss `fetch(url, { cf: { cacheTtl, cacheEverything: true } })`; при
недоступности GitHub отдаём последний успешный закэшированный вариант
(`stale-if-error`, §5.1 RFC 8484 упоминает эти директивы). Если апстрим
упал — SERVFAIL **сразу**, не тишина. Никакого cron, сверки версий, KV, D1.

**Синхронизация `id`** нужна только в режиме `lists`: приложение и воркер
используют один словарь `id → URL`, источник правды — `worker/lists.json`
в ветке; прессеты в приложении (`TunnelManager.proxyListPresets`) сверяются
с ним. Неизвестный `id` игнорируется — страховка рассинхрона. **В простом
режиме этой проблемы нет вовсе** — воркер про `id` не знает.

**Структура ветки `worker/`:**

```
worker/
  src/index.js        # DoH + /diagnose, ~80 строк в простом режиме;
                      # код MODE="lists" лежит рядом, выключен за MODE
  wrangler.toml
  lists.json          # id → name → URL; НУЖЕН ТОЛЬКО для MODE="lists"
  README.md           # деплой → TRUSTED_IDS (+ REQUIRE_ID) → скопируй host в приложение
  LICENSE
```

На **этапе 1** реально используются только `src/index.js`, `wrangler.toml`
и `README.md`; `lists.json` кладём сразу как заготовку для расширения, но
воркер его не читает.

CI `build.yml` на `main` эту ветку не трогает.

### 6.4. Что НЕ трогаем (базовый функционал)

функционал приложения наравне с системой Telegram: пользователь как мог
выбрать Cloudflare / Google / Яндекс / свой DoT / DoH / «Системный» в
«DNS-серверах», так и может. Ни `dnsPresets`, ни `activeDNSServers`, ни
`DNSView`, ни `DNSConfig` не удаляются и не переименовываются.

**По умолчанию теперь ВСЕГДА выбран «Системный» DNS** (`selectedDNSId =
"system"`). Приложение в первую очередь — про Telegram, поэтому новая
подсистема прокси-доменов не должна ничего менять в поведении «из коробки»:
включил туннель → работает ТГ, DNS устройства как был, сюрпризов нет.

«Прокси по доменам» и заполнил адрес воркера.

Соответственно `NEDNSOverHTTPSSettings` для воркера — **не замена**
обычного выборщика, а отдельная ветка: если режим прокси-доменов выключен,
`startTunnel` работает ровно как сейчас (системный DNS / выбранный пресетами
DoT-DoH / LRDNS-конфиг по старой логике — но см. §7, сам LRDNS-резолвер
из рабочего пути уходит).

Telegram** — остаются как есть и не переписываются.

### `startTunnel` — итоговые 5 точек

1. `dnsSettings = NEDNSOverHTTPSSettings(servers: [IP воркера])`,
   `serverURL = https://<host>/dns-query/<HWID>` (**без сегмента списков** —
   простой режим воркера, §1.2), **`matchDomains` = ТОЧНЫЕ домены из
   включённых `.lst` (Вариант Б)**. Никакого `[""]`, никакого eTLD+1.
   Список приходит из Main App в `providerConfiguration["matchDomains"]`
   (уже загруженные/дедуплицированные имена, без обрезки `prefix(250)` —
   ограничение снято, FakeIP теперь один на всех).
   **Именно здесь живёт вся фильтрация**; воркер отвечает FakeIP на любой
   дошедший запрос.
2. `includedRoutes = TelegramDCs.includedRoutes + 198.18.1.0/24`.
3. `excludedRoutes += IP воркера` (к уже существующему IP socks5-прокси).
4. `handleAccept`: **сначала** проверка `dcIP` на подсети Telegram →
   WSBridge-ветка (§4, приоритет незыблемый). Затем любой `dcIP` из
   `198.18.1.0/24` → сессия с `TLSSNI` →
   `ProxyClient.connect(domain: SNI, port: dstPort)`.
   Мапа IP→домен не нужна: **всегда один FakeIP, домен из SNI**.
5. UDP:443 → ICMP Port Unreachable (оставляем, фолбэк QUIC→TCP работает).
   Прочий UDP дропаем как раньше.

**Переключатель А/Б:** одна строка — убрать/вернуть `matchDomains`, плюс
переключить `MODE` воркера на `"lists"` и добавить сегмент списков в URL.
Держать в `providerConfiguration["dnsMode"]`, чтобы откат на этапе 2/5 не
требовал пересборки приложения. В простом режиме воркера (`MODE="simple"`)
Вариант А **не включать**: без фильтрации весь DNS получил бы FakeIP.

`CFBundle`/entitlements/CI/версионирование `X.Y.N` — **не меняем**.

## 8. Этапы реализации

Каждый этап заканчивается проверкой на живом iPhone; до прохождения
следующий не начинаем. Никаких «четырёх сборок догадок».

### Этап 0 — Откат эксперимента
Откатить незапушенные 26 CIDR + IPv6-маршруты к состоянию `0.3.16`.
Дерево чистое, превью не трогаем.
**Критерий:** `git diff` пуст, `WSB_BUILD` = 17 на origin.

### Этап 1 — Ветка `worker/` (изолированно, без приложения)
`src/index.js` (**простой режим `MODE="simple"`**), `wrangler.toml`,
`README.md`; `lists.json` кладём заготовкой, воркер его не читает.
DoH POST + GET, `REQUIRE_ID`/`TRUSTED_IDS`, FakeIP-метка на **любой**
валидный запрос, `/diagnose` JSON. Никаких `.lst`, апстрима, кэша — код
режима `MODE="lists"` оставляем рядом выключенным (§1.2).
**Критерий:** `curl` с валидным HWID → A=`198.18.1.1` **для любого домена**;
с левым HWID → REFUSED; при `REQUIRE_ID=false` → A=`198.18.1.1` даже без
HWID; `GET /diagnose` → ожидаемый JSON (`mode:"simple"`, `requireId`,
`wouldAnswer`). Проверяем **до** того, как приложение узнает про воркер.

### Этап 2 — Проверка главного риска (делается ПЕРВЫМ в приложении)
Минимальный тест: собрать `NEDNSOverHTTPSSettings` с URL
`https://<host>/dns-query/<HWID>` (**простой path, без сегмента списков**)
и с `matchDomains` из точных имён, включить туннель, посмотреть в логах
воркера, что path дошёл **и что запросы по доменам из `matchDomains`
реально приходят на воркер, а посторонние — нет**.
**Критерий:** воркер видит `/dns-query/<HWID>` и
`POST application/dns-message` по `gemini.google.com`; в `/diagnose`
`parsed.qname` заполнен; в логах **нет** `google.com` / `2ip.ru`.
Если path урезается — переходим на HWID в поддомене
(`<hwid>.host/dns-query`, `Host` не теряется никогда).
Если `dnsSettings` применён, `/diagnose` зелёный, **но запросов по домену
из списка нет** → это триггер отката на **Вариант А** (§1.1), одна строка.
**Это развилка, которую нельзя пропустить.**

### Этап 3 — Приложение: конфиг + UI
Поля по §6, `identifierForVendor`, склейка URL, кнопки копировать/тест/
инструкция, `.onDelete` для прокси, удаление Hosts и «Тест DNS».
**Критерий:** «Тест воркера» зелёный; HWID в UI совпадает с `TRUSTED_IDS`;
итоговый URL человек не собирает руками.

### Этап 4 — Туннель: снятие DNS-кода
Удаление по §7, `dnsSettings` на воркер, `excludedRoutes`, FakeIP-метка →
SNI → socks5.
**Критерий:** `udp53` больше не пишется; в журнале `proxy:conn…` /
`sni_proxy:gemini.google.com`; `mem` < 12 МБ.

### Этап 5 — Сквозной тест
- Telegram работает (WSBridge не тронут) **и при включённом пресете
  `telegram` в списках прокси-доменов не уходит в socks5** — проверка
  приоритета из §4: `accept:` для `149.154.x` → `init:conn…:DC…`, а не
  `proxy:conn…`;
- при первом запуске / после сброса настроек в выборщике DNS стоит
  «Системный»; обычные DNS-пресеты (Cloudflare, Google, Яндекс, свои DoT/DoH)
  доступны и работают как раньше;
- google.com, `2ip.ru`, YouTube открываются, резолвятся **системным DNS**
  (воркер их не видит — проверяем по логам воркера, это и есть Вариант Б);
- Gemini в Safari и в нативном приложении — без «не поддерживается в вашей стране»;
- rsync/видео не идут через туннель (`io:in` растёт только на целевых доменах);
- вкл/выкл туннеля 4 раза подряд — кнопка жива, ложных уведомлений нет;
- левый HWID в конфиге воркера → домены из списков получают REFUSED и
  **не проксируются**, но обычные сайты продолжают работать (их резолвит
  система, воркер их не видит); `/diagnose` показывает
  `HWID_NOT_TRUSTED`. Это и есть проверка «не юзали в злых целях» без
  побочного урона;
- `REQUIRE_ID = false` в `wrangler.toml` → воркер отвечает FakeIP без HWID,
  `/diagnose` показывает `ID_CHECK_DISABLED` (проверка параметра
  отключения защиты).

### Этап 6 — Документация и публикация
`README.ru.md`/`README.md`: новая архитектура, удаление Hosts, версионирование
`X.Y.N`. `worker/README.md`: деплой, `MODE`/`REQUIRE_ID`/`TRUSTED_IDS`,
смена HWID при переустановке, простота основного режима, и отдельным
разделом — как включить `MODE="lists"` (расширение) и когда это нужно.
Превью собирается CI автоматически; стабильный релиз — только по явной
команде и тегу `vX.Y.N`.

## 9. Риски и закрытые решения

| Риск | Митигация |
|---|---|
| Apple нормализует path/query в `serverURL` | Этап 2 до всего остального; fallback — HWID в поддомене (`Host`) |
| Path с `+` кодируется | `+` валиден в path; на этапе 2 проверить точное значение `url.pathname` |
| Бутстрап-петля «резолвим воркер через воркер» | `servers: [IP]` резолвится в Main App до старта (RFC 8484 §10) |
| Воркер за Cloudflare → DoH уедет в `utun` | `excludedRoutes += IP воркера` |
| Апстрим упал → тишина | **В простом режиме апстрима нет вовсе.** В `MODE="lists"` — SERVFAIL сразу + `stale-if-error` для списков |
| `mDNSResponder` шлёт GET, а не POST | воркер поддерживает оба (§4.1 RFC), QNAME из `?dns=base64url` |
| `identifierForVendor` сменился | UI показывает новый ID, инструкция говорит добавить его в allowlist |
| `REQUIRE_ID=false`, воркер открыт | Осознанный выбор пользователя; `/diagnose` показывает `ID_CHECK_DISABLED`; `matchDomains` всё равно ограничивает набор доменов |
| Кастомный список пользователя есть в приложении, но не в воркере | **В простом режиме проблемы нет** — воркер списков не знает, `matchDomains` строится приложением. При `MODE="lists"` добавляется в `worker/lists.json` руками |
| Весь DNS телефона на своём воркере (приватность) | **Вариант Б**: воркер видит только точные домены из включённых списков. В Варианте А (резерв) весь DNS идёт на свой же воркер — явно написать в README |
| `~5000` точных доменов в `matchDomains` | НЕ агрегируем, НЕ упрощаем до eTLD+1. Передаём как есть. Конфиг `providerConfiguration` держит массив строк; если упрёмся в лимит — делим на части, но не обобщаем |
| iOS не отдала домен из `matchDomains` на воркер | Ловится на этапе 2 по логам воркера → откат на **Вариант А** + `MODE="lists"` (§1.1, §1.2) |
| Поддомен попал под `matchDomains`, но его нет в `.lst` | **В простом режиме** воркер всё равно выдаёт FakeIP (фильтрация только на iOS) — это допустимо: раз домен попал в `matchDomains`, пользователь сам его туда включил. При `MODE="lists"` такие запросы идут на апстрим |
| Агрегат `google.com` вместо `gemini.google.com` | **ЗАПРЕЩЕНО**: потянет весь Google в прокси, лишняя нагрузка и риск незахвата критичного домена. Только точные имена из `.lst` |
| Простой воркер отвечает FakeIP на любой дошедший запрос | Не баг: `matchDomains` на iOS — единственный и достаточный фильтр. Плюс `REQUIRE_ID`/`TRUSTED_IDS`. Дублировать проверку в воркере — только в режиме `lists` |

**Развилка Б/А ЗАКРЫТА (решение принято):** основной — **Вариант Б**
(`matchDomains` = точные домены + **простой воркер `MODE="simple"`**),
**Вариант А** оставлен как резервный план отката: убрать `matchDomains` и
включить `MODE="lists"` с сегментом списков в URL (§1.1, §1.2). Код обоих
режимов воркера пишется сразу, но Lists-режим выключен. Открытых
архитектурных вопросов нет; до этапа 2 остаются только проверяемые факты
(доходит ли path, применяется ли `matchDomains`).

## 10. Что НЕ делаем (зафиксировано)

- ❌ мини-вебпанель, пароль, KV, D1, Durable Objects;
- ❌ автообновление по версии / cron / сверка изменений с GitHub;
  **в простом режиме нет и кэша/апстрима** — `caches.default` с TTL нужен
  только для `MODE="lists"`;
- ❌ `0/0`, замена lwIP на hev/tun2proxy, `NEDNSProxyProvider`;
- ❌ CIDR-угадывание, IPv6-костыли, `matchDomains=[""]`, FakeIP-мапа,
  `LocalDNSResolver`, Hosts, «Тест DNS»;
- ❌ общий публичный DoH-сервис (у каждого пользователя свой воркер);
- ❌ удаление обычного выборщика DNS / пресетов / DoT-DoH-настроек
  (базовый функционал, дефолт = «Системный», §6.4);
- ❌ какие-либо изменения в WSBridge-механизме Telegram: `CFDomains`,
  `WSClient`, `InitParser`, `MsgSplitter`, `AESCTR`, `TelegramDCs`,
  `startWS/startPipe` — не трогаем (§4);
- ❌ попадание Telegram-трафика в socks5/HTTP-прокси, даже если пресет
  `telegram` включён в списках (приоритет по IP датацентров, §4);
- ❌ агрегация/упрощение доменов до eTLD+1 (`google.com` вместо
  `gemini.google.com`) — только точные имена из `.lst` (§1.1);
- ❌ реализация Варианта А «сейчас» — он только резервный план отката,
  не переписываем под него архитектуру заранее (§1.1);
- ❌ **обработка списков `/ активных id` в воркере в основном режиме** —
  воркер не читает `.lst`, не знает про `id`, не форвардит на апстрим;
  вся фильтрация в `matchDomains` на iOS. Режим `MODE="lists"` — отдельное
  дальнейшее расширение и сразу план отката (§1.2).
