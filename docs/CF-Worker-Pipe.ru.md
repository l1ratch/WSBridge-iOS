# Свой Cloudflare Worker для WSBridge (pipe-режим)

Дата: 22.11.2026. Зачем: публичные фронты `kws*.<base>.co.uk` перегружены или
заблокированы — в журнале 0.3.32/0.3.34 они отвечают крошечными кадрами и
обрываются, а прямой 443 к гейтвею Telegram молчит. Свой воркер доходит до DC
**изнутри Cloudflare**, поэтому от сети пользователя зависит только участок
телефон → CF.

Код воркера: [`cf-worker-pipe.js`](./cf-worker-pipe.js) — официальный код
Flowseal/tg-ws-proxy ([docs/RU/CfWorker.md](https://github.com/Flowseal/tg-ws-proxy/blob/main/docs/RU/CfWorker.md)),
проверен побайтово на идентичность исходнику.

## Что должно совпадать (уже совпадает, менять код iOS не нужно)

| Сторона | Контракт |
|---|---|
| iOS `WSClient.connectPipe` | `wss://<домен>/apiws?dst=<IP>`, сырые байты в обе стороны |
| Воркер | `pathname === "/apiws"`, читает `dst`, `connect({hostname: dst, port: 443})` |

`dst` берётся из пакета Telegram, который принял lwIP: реальный IP DC
(`149.154.167.35` и т.п.), а не подменённый. Режим включается сам, как только
заполнено поле «CF Worker» — все телеграм-сессии уходят в `startPipe()`,
kws-каскад при этом не используется.

## Деплой (около 3 минут)

1. **Проверьте доступность `workers.dev` на телефоне** — это условие №1, без него
   всё остальное бессмысленно. Откройте в Safari на iPhone любой адрес
   `https://<что-нибудь>.workers.dev`. Если не открывается — добавьте в обход
   (zapret/другое ПО) домены `cloudflare.com`, `cloudflare.dev`, `workers.dev`,
   как рекомендует документация Flowseal.
2. [dash.cloudflare.com](https://dash.cloudflare.com/) → **Compute** →
   **Workers & Pages** → **Create application** → **Start with Hello World!** →
   **Deploy**. Имя возьмите новое, например `wsbridge-pipe`.
3. **Важно:** не перезаписывайте существующий DoH-воркер
   (свой домен вида <name>.workers.dev) - там другой код, он /apiws не
   обслуживает (проверено: отвечает текстом «WSBridge DoH worker»).
4. **Edit code** → стереть всё слева → вставить содержимое
   [`cf-worker-pipe.js`](./cf-worker-pipe.js) целиком → **Deploy**.
5. Проверка живости: откройте `https://<ваш-домен>` в браузере. Должно быть
   **`Expected websocket`** (HTTP 426). Это значит воркер задеплоен и ждёт
   WS-апгрейда — так и должно быть, браузер апгрейд не шлёт.

## Подключение в WSBridge

1. Меню → **CF Worker** → вписать домен вида `wsbridge-pipe.<аккаунт>.workers.dev`
   (без `https://`). Несколько доменов — через запятую, соединения
   распределяются round-robin.
2. Поле активно только при выключенном туннеле; после ввода перезапустите туннель.
3. Поле «DC → IP» работает и в этом режиме: формат `номер:IP` перенаправляет
   dial воркера. Если фото/видео не грузятся (аккаунт без Premium), документация
   Flowseal советует оставить только `4:149.154.167.220`.

## Что смотреть в журнале после включения

| Строка | Значит |
|---|---|
| `cfg:worker=<домен>(x1)` | настройка доехала до расширения |
| `pipe:conn<N>:<IP>` | сессия ушла в pipe-режим (не в kws-каскад) |
| `ws_ping` | WS до воркера реально открыт |
| `ws_up` + `ws_send:ok` | init ушёл, канал двусторонний |
| `pipe_remap:<A>-><B>` | сработало правило «DC → IP» |
| `ws_slow` | воркер не ответил за 7 с — см. ниже |
| `ws_pingerr` | WS не поднялся: домен недоступен или не задеплоен |

Если есть `ws_ping`, но нет `ws_up` — воркер жив, а его TCP к DC завис; это
уже сторона Telegram/DC, а не сети пользователя.

## Ограничения

- Лимит free-плана Cloudflare: 100 000 запросов в день на воркер. Для личного
  Telegram хватает, при активной загрузке медиа может не хватить.
- Участок телефон → CF остаётся шифрованным (WSS/443), участок CF → Telegram DC —
  обычный TCP:443 с obfuscated2 поверх (шифрование самого MTProto сохраняется).
- Это не проверка того, что Telegram точно заработает: результат зависит от
  доступности `workers.dev` и DC из вашего региона. Замер — по журналу выше.
