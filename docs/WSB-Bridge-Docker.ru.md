# WSBridge WS-мост на VDS (Docker)

Дата: 22.11.2026. **Статус: проверено на реальном устройстве, работает.**

```
iPhone (IPv4, любая сеть)  →  VDS:<port> (IPv4)  →  kws{dc} Telegram (IPv6)
```

**IPv6 нужен только на VDS.** Телефон подключается по обычному IPv4 —
мобильная сеть без IPv6 не помеха. Это и есть смысл моста: он сам
перекладывает IPv4-поток телефона в IPv6-соединение с Telegram.

Подтверждено боевым прогоном: 11 соединений, `err=0 silent=0`, включая
media-DC (`kws2-1`, `kws4-1`), до 1.2 КБ в обе стороны на сессию; на клиенте
`wd≈538 КБ` доставлено в Telegram за 15 с, соединения не рвутся.
Приложение при этом не менялось — хватило relay-режима, который в нём уже был.

## Почему так, а не иначе (измерено 22.11.2026)

| Путь | Результат |
|---|---|
| CF Worker → DC по IPv4 (все 6 канонических IP) | таймаут, 0 байт |
| CF Worker → `www.google.com:443` (контроль) | TLS ServerHello за 163 мс — egress воркера жив |
| CF Worker → `kws2` по IPv6 `[2001:67c:4e8:f004::9]` | TLS + `101` + **MTProto-ответ 103 B** |
| Все DC kws по IPv6 (1,2,3,4,5, media) | MTProto-ответ 103 B у каждого |
| Мост целиком (head → init → split → TLS → WS → MTProto) | **ответ 101 B вернулся клиенту**, `ok=1 silent=0` |

Вывод: IPv4-адреса Telegram фильтруются, IPv6-гейтвеи живые. Воркер в цепочке
не нужен — VDS и так имеет IPv6, лишнее звено только добавляет задержку и
лимит 100k запросов/день.

## Важные детали протокола (проверено)

- IPv6 в `connect()` нужно передавать **в квадратных скобках**; без них
  соединение рвётся мгновенно.
- В WS-апгрейде обязателен `Sec-WebSocket-Protocol: binary` — без него kws
  отвечает `404`, с ним `101`.
- Мост режет поток на MTProto-пакеты, расшифровывая **только префиксы длин**
  (как `MsgSplitter` в приложении). Payload не меняется — байты уходят как есть.
- Сплиттер проверен на abridged / abridged-big / intermediate / padded,
  целиком, кусками по 7 байт и побайтово: 12/12 тестов, все кадры байт-в-байт.

## Сборка и запуск

Порт выбирайте свободный: проверьте `sudo ss -tlnp`, затем откройте в UFW
(`sudo ufw allow <port>/tcp`). На типичном VDS 443/80/8443 заняты nginx,
2053/2083/2084 — контейнерами; из свободных хорошо смотрятся 2087, 2096, 9443.
Порт 2087 — «cPanel SSL», рядом с уже занятыми 2083/2084 выглядит естественно.

```bash
# на VDS, в папке с Dockerfile и wsb-ws-bridge.py
docker build -t wsb-bridge .

docker run -d --name wsb-bridge \
  --restart unless-stopped \
  --network host \
  wsb-bridge --port 2087

docker logs -f wsb-bridge

# открыть порт в фаерволе (обязательно: UFW по умолчанию дропает!)
sudo ufw allow 2087/tcp
sudo ufw status | grep 2087
```

Образ ~55 МБ (`python:3.12-alpine`), процесс под непривилегированным
пользователем, зависимостей нет. Если `total: 0` в stats при живом приложении —
порт закрыт фаерволом (см. выше); это самый частый стартовый затык.

### IPv6 в Docker

Контейнеру нужен **исходящий** IPv6. Проще всего — host-сеть (см. команду
запуска выше с `--network host`): контейнер использует стек хоста, где IPv6
уже работает. Bridge-сеть с IPv6 требует настройки демона Docker и не нужна.

Проверка IPv6 на хосте (должно вернуть `200`):
```bash
curl -6 -sS --max-time 8 https://ipv6.google.com -o /dev/null -w '%{http_code}\n'
```

## Подключение в WSBridge

1. Выключить туннель (поле активно только при выключенном).
2. Меню → **CF Worker** → `IP_вашего_VDS:2087` (порт — ваш из команды запуска).
3. Включить туннель.

Формат `host:port` включает relay-режим; приложение не меняется. В журнале
появится `cfg:worker=<ip>:2087(x1)` — значит, настройка доехала.

## Что смотреть

В журнале приложения:

| Строка | Значит |
|---|---|
| `cfg:worker=<ip>:2087(x1)` | настройка доехала |
| `pipe:conn<N>:<IP>` | сессия пошла через мост |
| `relay_up` | TCP до VDS открыт, заголовок ушёл |
| `ws_up` | **пришли байты от Telegram** — успех |
| `ws_recv:c<N>:n<K>:<bytes>` | кадры от Telegram идут потоком |
| `relay_slow` | VDS не ответил за 5 с: порт/фаервол |

На VDS: `docker logs -f wsb-bridge` — по каждому соединению видно
`open … DC2 -> [2001:67c:4e8:f004::9] kws2.web.telegram.org`,
`close … up=…B down=…B reply=True/False` и раз в минуту `stats: {…}`.

Ключевой счётчик — `silent`: соединения, где Telegram не ответил. Если
`ok` растёт, а `silent=0` — канал рабочий.

## Переопределение адресов

IPv6-гейтвеи получены через DoH 22.11.2026 и могут измениться. Обновить без
пересборки:

```bash
docker run -d --name wsb-bridge --network host wsb-bridge \
  --port 2087 \
  --dc6 2=2001:67c:4e8:f004::9 \
  --dc6 4=2001:67c:4e8:f004::9
```

Актуальные адреса:
```bash
curl -s 'https://dns.google/resolve?name=kws2.web.telegram.org&type=AAAA'
```

## Маскировка: чтобы DPI не распознал и не убил VDS

Угроза двух видов: (а) DPI оператора видит «подозрительный» трафик телефон→VDS
и режет/банит; (б) хостер получает жалобу на «прокси». Ниже — по уровням, от
бесплатного к сложному. Всё проверено на боевом стенде 22.11.2026, кроме
отмеченного «требует доработки».

### Уровень 0. Ничего не делать (рабочий минимум)

Для 1–2 пользователей профиль низкий: десятки соединений в день, мегабайты
трафика. Порт 2087 («cPanel SSL») рядом с обычными 2083/2084 смотрится
естественно. Первый пакет `wsb1 <ip>\n` не является HTTP — HTTP-классификаторы
его не распознают как веб и обычно игнорируют. **Начните с этого.**

### Уровень 1. Спрятать за nginx на 443 (рекомендую следующим шагом)

На VDS уже есть nginx на 443. Пусть снаружи будет только 443, а мост слушает
`127.0.0.1:2087`. DPI видит обычный HTTPS-порт; чтобы отличить наш трафик от
веба, нужен активный пробинг или анализ поведения.

nginx `stream`-модуль (прозрачный TCP-прокси, TLS не терминирует):
```nginx
# /etc/nginx/nginx.conf, блок stream (рядом с http)
stream {
    map $ssl_preread_server_name $backend {
        default              127.0.0.1:8443;   # обычный сайт
        bridge.example.com   127.0.0.1:2087;   # наш мост
    }
    server {
        listen 443;
        ssl_preread on;
        proxy_pass $backend;
    }
}
```
Но наш клиент шлёт сырой TCP без TLS-SNI, поэтому `ssl_preread` его не
различит. Реальный вариант — **SNI-роутинг не нужен**, просто отдельный
`server` на 443 с `proxy_pass 127.0.0.1:2087` и `ssl_preread` для остального.
Проще всего: выделенный IP или порт 443 только под мост, если сайт не нужен.

**Важно:** это требует, чтобы клиент говорил TLS (см. уровень 2), иначе nginx
на 443 отдаст сырой поток как есть — что тоже работает, но не маскирует.

### Уровень 2. TLS-обёртка клиент→VDS (требует доработки приложения)

Сделать участок телефон→VDS настоящим TLS 1.3 с валидным сертификатом
(Let's Encrypt на домен VDS). Тогда трафик неотличим от обычного HTTPS:
ClientHello с обычным SNI, стандартные шифры, ALPN `h2`/`http/1.1`.

Что нужно:
- на VDS: nginx/Caddy терминирует TLS на 443, проксирует расшифрованный поток
  на `127.0.0.1:2087`;
- в приложении: `connectRelay` сейчас шлёт сырой TCP — добавить TLS-опцию
  (`NWParameters.tls` с `NWProtocolTLS.Options`), это ~30 строк в
  [WSClient.swift](../Tunnel/WSClient.swift) и переключатель в UI.

Это самый надёжный вариант против DPI, но требует изменения кода приложения.
Не делаю без явной команды — сначала уровни 0–1.

### Уровень 3. Поведенческая маскировка (без кода)

- Не держать туннель включённым 24/7, если не нужен: меньше профиль.
- Один VDS — один пользователь. Массовость привлекает внимание.
- Не публиковать IP/домен VDS нигде (в этом репозитории их нет и не будет).
- Ротация порта раз в несколько месяцев, если появится подозрение на бан.

### Чего НЕ делать

- Не использовать «голый» MTProto-proxy на стандартном 443 без TLS — его
  DPI уже умеет распознавать (именно это и сломалось в ноябре).
- Не полагаться на «секретный» протокол `wsb1` как на защиту: это не
  криптография, а лишь маркер. Содержимое защищает MTProto end-to-end.

## Ограничения

- Мост в РФ: риск жалобы хостеру остаётся. Уровни 1–2 снижают риск DPI,
  но не отменяют юридический/хостерский.
- `IDLE_TIMEOUT=600` с: соединение без трафика 10 минут закрывается.
- Сертификат kws проверяется (цепочка + имя). Для отладки есть `--insecure`,
  в проде не нужен.
- MTProto-шифрование end-to-end сохраняется: мост видит только obfuscated2-поток,
  ключей сессии и содержимого у него нет.
